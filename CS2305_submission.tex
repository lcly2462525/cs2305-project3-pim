\begin{abstract}
For over half a century the Von Neumann architecture---a processor separated
from memory by a shared bus---has been the foundation of general-purpose
computing. As workloads turn data-intensive, the time and energy of moving data
between memory and processor now dominate, a limitation known as the
\emph{memory wall}. Processing-in-Memory (PIM) responds by computing inside or
beside the memory, where the data already resides. This report defines both
paradigms, argues that PIM is an evolutionary complement rather than a
replacement, and surveys where each fits---Von Neumann for control-intensive
work, PIM for data-movement-bound tasks such as AI inference and graph
analytics---concluding that future systems will be hybrid.
\end{abstract}

\section{Introduction}
For decades, most general-purpose computers have been built around the Von Neumann architecture, where a processor exchanges both instructions and data with a separate memory over shared communication paths. The model succeeded because it offers a simple, flexible abstraction: programs are stored in memory, fetched, and executed step by step. But as applications turn data-intensive, this separation of computation and storage has become a major performance and energy bottleneck---the \textit{memory wall}: processor performance has improved far faster than memory latency and bandwidth, so many workloads now spend more time waiting for data than computing. The problem is acute in artificial intelligence, database analytics, graph processing, and scientific computing. Processing-in-Memory (PIM)---near-memory or in-memory computing---addresses this by moving computation closer to or inside memory, giving memory an active role rather than treating it as passive storage. This report compares the two paradigms: their definitions, relationship, applications and the problems they solve, and implications for future systems.

\section{Basic Definitions}
\label{sec:def}


\subsection{Von Neumann Architecture}
\label{sec:vn}

The Von Neumann architecture is a classical model in which a central processing
unit communicates with a memory that stores both program instructions and data.
It is based on the \textit{stored-program concept}: instructions are represented
as data in memory and fetched by the processor for execution
\citep{hennessy2017computer}. This unified memory model---one space for both code
and data---makes the architecture flexible and well suited to general-purpose
computing.

A typical system consists of a processor, memory, input/output devices, and
interconnection buses. The processor combines an Arithmetic Logic Unit (ALU) for
arithmetic and logic with a Control Unit that fetches, decodes, and executes
instructions. Memory holds both instructions and operands, and system buses
carry data, addresses, and control signals between the processor, memory, and
peripherals \citep{hennessy2017computer}.

Although the Von Neumann architecture has supported decades of successful
computer system design, its separation between computation and storage creates a
major limitation. Since instructions and data must be repeatedly transferred
between the processor and memory, system throughput can be constrained by memory
latency and bandwidth. This limitation is commonly referred to as the
\textit{Von Neumann bottleneck} or, more broadly, the \textit{memory wall}
\citep{wulf1995memory}. This bottleneck is one of the main motivations for
exploring alternative architectures such as Processing-in-Memory.



\subsection{Processing-in-Memory (PIM)}
\label{sec:pim}

To relieve these performance limits, Processing-in-Memory (PIM) integrates computational capability directly inside or adjacent to the memory subsystem \citep{sebastian2020memory,mutlu2021primer}. Its central philosophy is to shift from bringing data to computation toward bringing computation to the data.

PIM falls into two broad categories. Near-Memory Computing (NMC) places processing elements or logic layers close to the memory arrays, such as a logic die beneath a 3D memory stack. In-Memory Computing (IMC) performs calculations directly within the arrays by exploiting the analogue physical properties of memory devices, as in ReRAM crossbars or modified SRAM \citep{ielmini2018inmemory}. Both shift from a compute-centric to a data-centric approach.

Practical implementations of the near-memory approach are emerging through technologies like High Bandwidth Memory (HBM), where DRAM dies are stacked vertically and connected to a base logic die through silicon vias, providing a location where simple processing elements can be embedded close to the data \citep{kwon2021hbmpim}. For in-memory logic, emerging non-volatile memory technologies such as ReRAM enable analog computation within the memory crossbar itself, accelerating matrix-vector multiplications fundamental to neural networks \citep{chi2016prime,shafiee2016isaac}.

The primary strengths of PIM are twofold. First, it provides access to massive internal memory bandwidth by enabling parallel interaction with the memory bank's wide internal data paths. Second, it significantly reduces energy consumption by eliminating the costly off-chip data transfers that dominate a conventional system's power budget \citep{horowitz2014energy}.

These advantages come with challenges: a complex programming model that breaks the single-address-space abstraction, immature compilation toolchains, changes to memory consistency models, and limited generality on control-flow-heavy tasks. Work must be explicitly partitioned between host and PIM units---a trade-off current hybrid systems actively navigate.

\section{Relationship Between Them}
\label{sec:rel}

\subsection{Evolutionary Perspective}

The relationship between PIM and the classical Von Neumann architecture is best viewed as evolutionary rather than a revolutionary displacement. PIM is not a complete replacement; it is an architectural complement and extension developed to overcome the physical limits of traditional systems under modern workloads.

For decades the Von Neumann model sustained the industry through its clean abstractions. But the memory wall---where the time and energy of moving data across a chip interface dwarf the arithmetic itself \citep{horowitz2014energy}---has made pure compute-centric scaling unsustainable, a friction worsened by data-intensive applications such as deep learning, graph analytics, and real-time databases. PIM evolves the infrastructure by embedding processing into memory-bound sectors, so computation can be dispatched to the CPU or to the memory depending on data locality---a more physically distributed but logically coherent system that evolves the Von Neumann paradigm rather than discarding it.

\subsection{Key Differences}

The fundamental divergence is one of data-handling philosophy: compute-centric versus data-centric. Von Neumann systems route all data through narrow buses to a central CPU, maximizing general programmability but penalizing massive datasets. PIM instead executes operations where the data resides, maximizing internal parallelism and suppressing off-chip communication, which shifts the dominant energy cost from expensive off-chip accesses to low-power near-array operations. \subsection{Hybrid Architectures}

Driven by these trade-offs, modern computer engineering increasingly favours hybrid, heterogeneous architectures. Rather than abandoning Von Neumann principles, systems adopt a cooperative CPU + PIM design \citep{mutlu2021primer}: a standard Von Neumann processor acts as the host---managing control logic, OS scheduling, and general tasks---and offloads heavy data-bound kernels, such as neural-network matrix multiplications or graph-traversal vector updates, to a PIM-enabled memory stack or accelerator.

A concrete example is an AI training accelerator coupling an HBM stack, whose base logic die performs near-memory weight updates and reductions, while a conventional CPU orchestrates the training loop. This synergy balances the programmability and mature ecosystem of the Von Neumann model for general tasks against the high-bandwidth, energy-efficient scaling of PIM for massive datasets. The future points not to a single victorious architecture but to a deep, collaborative integration of both.

\section{Application Scenarios and Problems Solved}
\label{sec:app}

\subsection{Problems Addressed}
The central problem is the \emph{memory wall}: for decades processor throughput
has grown faster than memory bandwidth, so performance is increasingly limited
by how fast operands reach the processor rather than by arithmetic
itself~\citep{wulf1995memory}. The cost is also energetic---an arithmetic
operation costs a few picojoules, while fetching its operands from off-chip DRAM
costs two to three orders of magnitude more, so in data-intensive systems data
movement, not computation, dominates energy and
latency~\citep{horowitz2014energy}. PIM attacks this directly by computing where
data already lives, removing much of the traffic the bus and cache hierarchy
struggle to sustain~\citep{sebastian2020memory,mutlu2021primer}.

\subsection{Applications of the Von Neumann Architecture}
The classical model remains the right choice for general-purpose and
control-intensive workloads---operating systems, compilers, and branch-heavy
application or transaction logic. These tasks are dominated by control flow and
irregular data access: they reuse little data per fetch and need low-latency
access to a flat address space rather than raw streaming bandwidth, so bus
bandwidth is rarely the binding constraint and the model's flexibility and
mature software make it the most productive target. Its weakness appears only in
the opposite regime---once a workload becomes data-movement-bound, the
centralised design forces costly round trips and the memory wall dominates.

\subsection{Applications of PIM}
PIM targets exactly those data-intensive workloads. The flagship case is
AI/deep-learning inference, dominated by matrix--vector multiplication: in a
resistive (ReRAM) crossbar, multiply--accumulate is performed in place by Ohm's
and Kirchhoff's laws, so the weights never move; accelerators such as
ISAAC~\citep{shafiee2016isaac} and PRIME~\citep{chi2016prime} exploit this for
large energy and throughput gains. Near-memory designs instead keep digital
logic but move it beside storage---Samsung's HBM-PIM embeds programmable compute
units in an HBM2 stack and raises effective bandwidth for machine-learning
kernels through bank-level parallelism~\citep{kwon2021hbmpim}. Beyond AI, real
general-purpose PIM hardware now exists: the UPMEM system places thousands of
cores inside DRAM and accelerates memory-bound tasks such as database
scan/filter, graph processing (BFS, PageRank), and
bioinformatics~\citep{gomezluna2022benchmarking}. The common thread is a high
data-to-compute ratio; the cost is limited precision and device variability in
analog crossbars and an immature programming model, so gains are
workload-dependent~\citep{ielmini2018inmemory}. Figure~\ref{fig:apps} summarises
where each paradigm is applied.

\section{Personal Reflections and Conclusions}
\label{sec:conc}
Our comparison yields a clear insight: the Von Neumann architecture is not
obsolete, and PIM is not a universal replacement. PIM solves one specific,
increasingly dominant problem---the cost of moving data---rather than
computation in general. Where a workload is bound by control flow or reuses
little data, the classical model's flexibility and mature software ecosystem
remain decisive; where a workload is bound by data movement, computing in or
near memory removes the traffic that throttles a conventional system.

The central trade-off is generality versus specialisation. The Von Neumann
model offers a single, flat memory abstraction and a universal programming
target, at the price of the memory wall. PIM offers enormous internal bandwidth
and energy efficiency, at the price of a harder programming model, weaker
generality, and, for analog in-memory designs, limited precision. Because
neither dominates across all metrics, real systems must choose per workload.

Looking forward, we expect heterogeneous, data-centric computing to become the
norm: a Von Neumann host orchestrating general logic while offloading data-bound
kernels to PIM accelerators, as already seen in commercial HBM-PIM products. The
harder bottleneck may be software rather than hardware---without standard
compilers, libraries, and consistency models, PIM's raw hardware gains are
difficult to realise in practice, and AI's appetite for memory bandwidth will
keep driving this evolution.

We therefore conclude that the future is not a single victorious architecture
but a collaborative integration of both: Von Neumann cores and PIM accelerators
coexisting to balance flexibility and efficiency. For us, the most valuable
lesson was learning to reason about computing in terms of data movement and
energy, not merely operation count---a perspective we expect to carry into
future study and work on AI hardware and systems.

\section{Optional: A Brief Case Study}
\label{sec:case}
A single example makes the contrast concrete. Consider a matrix--vector product
$y = Wx$ with an $N\times N$ weight matrix. On a Von Neumann processor each of
the $N^2$ weights must be read from memory and carried across the bus to the ALU
for one multiply--accumulate, so data movement scales as $N^2$ and dominates
time and energy. In a ReRAM crossbar the same operation is computed in
place---weights are stored as cell conductances and the result is obtained in
essentially one analog step via Ohm's and Kirchhoff's laws, so the weights never
move~\citep{shafiee2016isaac,sebastian2020memory}. This single kernel captures
why PIM wins on data-movement-bound work, while Von Neumann wins where control
flow dominates.
